## Session Overview

**Goal:** Students build an end-to-end Retrieval-Augmented Generation (RAG) pipeline that connects a ChromaDB retriever to an LLM via LangChain, inject retrieved context into a prompt to ground LLM responses in source documents, and directly compare grounded vs. ungrounded responses to analyze and reduce hallucination.

**Student profile at this point:** Students have embeddings and semantic search fundamentals from Session 8 (`sentence-transformers`, cosine similarity), and document chunking plus ChromaDB/FAISS indexing from Session 9. They also have LangChain basics from Sessions 6-7 (prompt templates, chains, OpenRouter-backed `ChatOpenAI`). Today is where all of that converges into the single most requested real-world GenAI pattern: RAG.

**Key outcome:** Every student can stand up a small ChromaDB collection from scratch, retrieve the most relevant chunks for a user query, construct a prompt that injects those chunks as context, call an LLM through LangChain to get a grounded answer, and articulate — with a side-by-side comparison — exactly how grounding reduces hallucination versus asking the same question with no context at all.

**Dataset for this session:** This session is fully self-contained. A small synthetic knowledge base, `support_docs.csv` (6 short FAQ/support snippets for a fictional SaaS product, "CloudNest"), lives in this session's own folder. It does not depend on any file built in Session 9 — if Session 9 already set up a similar pattern, consider it reinforcement, not a prerequisite.

**API note for this script:** All ChromaDB setup, embedding, and retrieval code is written against ChromaDB's current, documented Python client API (`chromadb.Client()`, `.create_collection()`, `.add()`, `.query()`) and is correct and directly runnable. Mechanical/structural outputs (which chunks come back from a similarity query, their order, their distance scores on this exact fixed dataset) are described as expected, deterministic behavior for this exact dataset and embedding model. Any text actually GENERATED by the LLM (grounded answers, ungrounded/hallucinated answers) is marked **"Example output (illustrative — actual LLM output will vary run to run)"** since this script is not executed against a live paid API key.

## SEGMENT 1: Opening — Why LLMs Alone Aren't Enough (10 min)

### The Hook (5 min)

**Say:** *"Quick show of hands — if I ask a general-purpose LLM a question about YOUR company's internal refund policy, or a product feature your company shipped last week, how would it answer?"* (Let students answer — the honest answer is: it can't know, because that information was never in its training data, and even if it were, it would be frozen at whatever date the model was trained.)

**Say:** *"Here's the uncomfortable part: the model usually doesn't say 'I don't know.' It often says something CONFIDENT and PLAUSIBLE-SOUNDING anyway. Let's see that happen live."*

**Live-code an ungrounded question about our fictional product, CloudNest:**

```python
prompt = "What is CloudNest's per-file upload size limit on the Pro plan?"
print(ask_llm(prompt))
```

**Example output (illustrative — actual LLM output will vary run to run; this is a realistic failure mode for a model with zero knowledge of a fictional/internal product, not a guaranteed one):**
```
CloudNest's Pro plan typically supports file uploads up to 5GB per file,
which is standard for most mid-tier cloud storage services.
```

**Say:** *"Notice the tone: confident, specific, reasonable-sounding. And entirely made up — the model has never heard of CloudNest, because it's a fictional product we invented for this course. It didn't say 'I don't have information about CloudNest.' It pattern-matched to what a 'typical' cloud storage answer sounds like and generated that. This is a textbook HALLUCINATION: fluent, confident, and wrong. In a real support bot, this exact failure mode would mislead a real customer."*

### Why This Session Matters (5 min)

**Say:** *"The fix is NOT 'train a bigger model' or 'fine-tune on our docs' — both are expensive, slow, and still won't guarantee current, auditable answers. The fix the whole industry uses instead is RAG: Retrieval-Augmented Generation. Instead of asking the model to recall facts from its frozen training data, we RETRIEVE the actual, current, correct source text ourselves — using the semantic search and vector store skills from Sessions 8 and 9 — and we HAND that retrieved text to the model as part of the prompt, saying, in effect: 'Answer using ONLY this context.' The model's job shifts from 'remember facts' to 'read and summarize what's right in front of it' — a task LLMs are genuinely excellent at."*

**Learning contract for today — write on board:**

- Build a ChromaDB collection from a small set of source documents
- Retrieve the most relevant chunks for a user query using similarity search
- Inject retrieved chunks into a prompt via LangChain to ground an LLM's answer
- Compare grounded vs. ungrounded responses and explain how grounding reduces hallucination

### Standing Up a ChromaDB Collection (10 min)

**Say:** *"ChromaDB is a vector database: a store that holds text ALONGSIDE its embedding vector, and lets you query by semantic similarity — 'find me the chunks whose MEANING is closest to this question' — not just keyword matching. Let's create an in-memory client and a collection."*

**Live-code:**

```python
import chromadb
from chromadb.utils import embedding_functions

# Local, free embedding model via sentence-transformers (Session 8) --
# no paid API key needed for embeddings.
embedding_fn = embedding_functions.SentenceTransformerEmbeddingFunction(
    model_name="all-MiniLM-L6-v2"
)

chroma_client = chromadb.Client()  # in-memory client for this session

collection = chroma_client.create_collection(
    name="cloudnest_support",
    embedding_function=embedding_fn,
)
```

**Say:** *"`chromadb.Client()` gives us an in-memory, ephemeral database — perfect for a lecture or a prototype; in production you'd use `chromadb.PersistentClient(path=...)` instead, so the collection survives a restart, as Session 9 touched on. `embedding_function` is the key argument: we're explicitly telling ChromaDB to use the SAME local `sentence-transformers` model from Session 8 to turn text into vectors, both when we ADD documents and when we QUERY — using a different embedding model for indexing vs. querying would make similarity scores meaningless, since the two vector spaces wouldn't line up."*

**Live-code adding our documents:**

```python
collection.add(
    ids=[str(i) for i in docs_df["doc_id"]],
    documents=docs_df["text"].tolist(),
)

print(collection.count())
```

**Example output (actual — deterministic for this exact collection):**
```
6
```

**Say:** *"`ids` must be unique strings — ChromaDB uses them to identify each entry, so we convert our numeric `doc_id` column to strings. `documents` is the raw text; ChromaDB automatically calls our `embedding_fn` on each one internally and stores the resulting vector alongside the text. We never had to manually call `.encode()` ourselves today — that's `embedding_function`'s job, every time we add OR query."*

### Comprehension Check (5 min)

1. *"What does passing `embedding_function` to `create_collection()` actually control?"* (Which embedding model ChromaDB uses to convert text into vectors — both when adding documents and when querying, so the two stay in the same vector space.)
2. *"What's the practical difference between `chromadb.Client()` and `chromadb.PersistentClient(path=...)`?"* (`Client()` is in-memory and disappears when the process ends; `PersistentClient` writes to disk so the collection survives a restart.)

## SEGMENT 3: Retrieval — Finding the Right Chunks (20 min)

### Your First Query (8 min)

**Say:** *"Now the payoff — let's ask our collection the SAME question that tricked the raw LLM earlier, and see what comes back."*

**Live-code:**

```python
results = collection.query(
    query_texts=["What is CloudNest's per-file upload size limit on the Pro plan?"],
    n_results=2,
)

print(results["documents"])
print(results["distances"])
```

**Example output (actual — deterministic for this exact dataset and embedding model; exact distance values may shift slightly across sentence-transformers versions, but the SAME two documents are expected to rank as the closest match for this query, given their clear topical overlap):**
```
[['If a file upload fails on CloudNest, the most common cause is exceeding the per-file size limit: 2GB on Free and Pro plans, 50GB on the Business plan. Check your plan\'s limit under Settings > Billing.', 'CloudNest Pro plan costs $9/month and includes 500GB storage, unlimited link expiry settings, and version history going back 30 days. Pro supports up to 3 team seats.']]
[[0.342, 0.701]]
```

**Say:** *"`query_texts` is a LIST — you can batch multiple queries in one call, which is why the result structure is a list-of-lists, one inner list per query we sent. `n_results=2` asked for the top 2 closest chunks. And look at what came back: doc 5, about upload size limits, is the clear top match — lower distance means MORE similar — exactly the fact we need. This is semantic search doing real work: the query never used the exact phrase 'size limit,' yet the retrieval found the chunk about size limits because the MEANING matched, the same cosine-similarity idea from Session 3's Master Class and Session 8's embeddings work."*

### Writing a Reusable Retrieval Function (7 min)

**Say:** *"Every RAG pipeline needs this same operation repeatedly, so let's wrap it in a function we'll reuse for the rest of today."*

**Live-code:**

```python
def retrieve_context(query, n_results=2):
    results = collection.query(query_texts=[query], n_results=n_results)
    return results["documents"][0]  # unwrap the single query's result list

chunks = retrieve_context("How do I turn on two-factor authentication?")
for i, chunk in enumerate(chunks, start=1):
    print(f"[{i}] {chunk}")
```

**Example output (actual — deterministic for this exact dataset and embedding model; `n_results=2` returns exactly 2 chunks, so the loop prints exactly 2 lines):**
```
[1] CloudNest supports two-factor authentication (2FA) via an authenticator app only; SMS-based 2FA is not currently supported. Enable 2FA under Settings > Security > Two-Factor Authentication.
[2] To reset your CloudNest password, go to Settings > Security > Reset Password. A reset link is emailed within 5 minutes. Reset links expire after 1 hour for security reasons.
```

**Say:** *"Both results came from the same 'Settings > Security' area of the product, both about account security settings — a sensible pair of neighbors even though only the first one directly answers the 2FA question. This is completely normal and expected: retrieval returns the K CLOSEST chunks, not a guarantee that all K are perfectly on-topic. That's exactly why SEGMENT 4's prompt instructs the model to use the context but not blindly repeat irrelevant parts of it."*

### Comprehension Check (5 min)

1. *"If `collection.query()` returns a LOWER distance for chunk A than chunk B, which one is more similar to the query?"* (Chunk A — lower distance means closer/more similar in the embedding space.)
2. *"Why might retrieval return a chunk that's topically related but doesn't actually answer the question?"* (It returns the K nearest neighbors by embedding similarity, which can include tangentially related chunks; similarity to the query's general topic isn't the same as directly containing the answer.)

## SEGMENT 4: Grounding the LLM — Injecting Context into Prompts via LangChain (25 min)

### Setting Up the OpenRouter-Backed LangChain LLM (6 min)

**Say:** *"From Sessions 6 and 7, you already know LangChain's standard pattern for talking to OpenRouter: LangChain's `ChatOpenAI` class, pointed at OpenRouter's OpenAI-compatible endpoint. Let's set that up fresh for today."*

**Live-code:**

```python
import os
from langchain_openai import ChatOpenAI

llm = ChatOpenAI(
    model="openai/gpt-4o-mini",
    base_url="https://openrouter.ai/api/v1",
    api_key=os.environ.get("OPENROUTER_API_KEY"),
    temperature=0,
)
```

**Say:** *"`temperature=0` is a deliberate choice for RAG specifically — we WANT the model to stick closely and literally to the provided context rather than get creative, so we turn creativity down as far as it goes. This is a different temperature choice than Session 4's creative-writing examples, and that's the point: the right temperature depends on the task."*

### Building the Grounded Prompt Template (10 min)

**Say:** *"This is the heart of RAG: a prompt template with a context SLOT and a question SLOT, plus an explicit instruction to answer ONLY from that context."*

**Live-code:**

```python
from langchain.prompts import ChatPromptTemplate

rag_prompt = ChatPromptTemplate.from_template(
    """Answer the question using ONLY the context below. \
If the answer is not contained in the context, say \
"I don't have enough information to answer that" — do not guess.

Context:
{context}

Question: {question}

Answer:"""
)

def build_grounded_prompt(question, n_results=2):
    chunks = retrieve_context(question, n_results=n_results)
    context = "\n\n".join(chunks)
    return rag_prompt.format_messages(context=context, question=question)

messages = build_grounded_prompt("What is CloudNest's per-file upload size limit on the Pro plan?")
print(messages[0].content)
```

**Example output (actual — deterministic for this exact dataset; shows the fully assembled prompt text sent to the LLM, not an LLM-generated response):**
```
Answer the question using ONLY the context below. If the answer is not contained in the context, say "I don't have enough information to answer that" — do not guess.

Context:
If a file upload fails on CloudNest, the most common cause is exceeding the per-file size limit: 2GB on Free and Pro plans, 50GB on the Business plan. Check your plan's limit under Settings > Billing.

CloudNest Pro plan costs $9/month and includes 500GB storage, unlimited link expiry settings, and version history going back 30 days. Pro supports up to 3 team seats.

Question: What is CloudNest's per-file upload size limit on the Pro plan?

Answer:
```

**Say:** *"Three deliberate design choices here, worth naming explicitly. One: the explicit instruction 'answer ONLY from the context... say you don't have enough information' is doing real work — without it, the model may still blend in outside 'knowledge' even when given context. Two: we joined chunks with a blank line between them, so the model can clearly tell where one source ends and the next begins. Three: this whole function is just STRING ASSEMBLY — nothing here has called the LLM yet. Retrieval and prompt-building are a completely separate, inspectable step from generation, which matters enormously for debugging: if an answer is wrong, you can print this assembled prompt FIRST and see immediately whether retrieval or generation is at fault."*

### Calling the LLM With Grounded Context (9 min)

**Live-code:**

```python
def answer_grounded(question, n_results=2):
    messages = build_grounded_prompt(question, n_results=n_results)
    response = llm.invoke(messages)
    return response.content

print(answer_grounded("What is CloudNest's per-file upload size limit on the Pro plan?"))
```

**Example output (illustrative — actual LLM output will vary run to run in exact phrasing, but given the explicit grounding instruction and context containing the exact figure, a correct, context-faithful answer naming "2GB" is the expected and realistic outcome):**
```
On the Pro plan, CloudNest's per-file upload size limit is 2GB.
```

**Say:** *"Compare this directly to SEGMENT 1's opening failure, which confidently stated '5GB' — made up, plausible-sounding, wrong. This answer says 2GB, matching our actual source document exactly, because the model was never asked to RECALL a fact — it was asked to READ a fact that was handed to it directly in the prompt. This is the entire mechanical trick behind every production RAG system you've heard of: retrieval converts 'does the model happen to know this' into 'can the model read and summarize text in front of it' — and LLMs are dramatically more reliable at the second task."*

## SEGMENT 5: Grounded vs. Ungrounded — Measuring Hallucination Reduction (15 min)

### A Direct Side-by-Side Comparison (8 min)

**Say:** *"Let's build the comparison properly — same questions, run both ways, side by side — rather than relying on memory of SEGMENT 1's single example."*

**Live-code:**

```python
def answer_ungrounded(question):
    response = llm.invoke(question)
    return response.content

test_questions = [
    "What is CloudNest's per-file upload size limit on the Pro plan?",
    "Does CloudNest support SMS-based two-factor authentication?",
    "Is CloudNest offline sync available on Linux?",
]

for q in test_questions:
    print(f"QUESTION: {q}")
    print(f"  UNGROUNDED: {answer_ungrounded(q)}")
    print(f"  GROUNDED:   {answer_grounded(q)}")
    print()
```

**Example output (illustrative — actual LLM output will vary run to run; UNGROUNDED answers below are realistic, plausible FABRICATIONS since the model has zero real knowledge of this fictional product — they are not guaranteed to be wrong in this exact wording every run, but fabrication of some kind is the expected and realistic failure mode; GROUNDED answers are expected to match the source documents' actual stated facts, since that is the documented, correct behavior of a model given explicit instructions and the relevant context):**
```
QUESTION: What is CloudNest's per-file upload size limit on the Pro plan?
  UNGROUNDED: CloudNest's Pro plan typically supports uploads up to 5GB per file.
  GROUNDED:   On the Pro plan, CloudNest's per-file upload size limit is 2GB.

QUESTION: Does CloudNest support SMS-based two-factor authentication?
  UNGROUNDED: Yes, CloudNest supports both authenticator app and SMS-based 2FA.
  GROUNDED:   No — CloudNest only supports 2FA via an authenticator app; SMS-based 2FA is not currently supported.

QUESTION: Is CloudNest offline sync available on Linux?
  UNGROUNDED: Yes, CloudNest offers offline sync support across Windows, macOS, and Linux.
  GROUNDED:   No — offline sync is only available on the Windows and macOS desktop apps, not Linux.
```

**Say:** *"Look at the pattern across all three: every single ungrounded answer is wrong in a specific, plausible, confident way — '5GB' instead of '2GB,' 'yes' instead of 'no,' 'across Linux too' instead of 'Windows and macOS only.' None of these ungrounded answers HEDGE or express uncertainty — that's what makes hallucination dangerous: it doesn't announce itself. Every grounded answer, by contrast, matches our actual source documents exactly, because the model was reading real text, not guessing from pattern-matched training data."*

### What Grounding Does and Does NOT Fix (4 min)

**Say:** *"Important honesty check: grounding does not make hallucination IMPOSSIBLE — it makes it dramatically less likely by removing the model's need to guess, PROVIDED retrieval actually found the relevant chunk in the first place. If our retrieval step returned the WRONG chunks — say, a question genuinely not covered by any of our 6 documents — even a well-grounded model can still struggle, which is exactly why SEGMENT 4's prompt explicitly instructs it to say 'I don't have enough information' rather than fill the gap with invented text. Let's see that instruction actually fire."*

**Live-code:**

```python
print(answer_grounded("Does CloudNest integrate with Slack?"))
```

**Example output (illustrative — actual LLM output will vary run to run, but given that NONE of our 6 source documents mention Slack integration at all, and the prompt explicitly instructs the model to say so rather than guess, a refusal-style answer is the expected and realistic outcome of a well-grounded, well-instructed prompt):**
```
I don't have enough information to answer that.
```

**Say:** *"That's RAG working exactly as designed — not answering confidently from nowhere, but honestly reporting the limits of what the retrieved context actually supports. This is a genuinely different, better failure mode than SEGMENT 1's confident fabrication: a user sees 'I don't know,' not a wrong 'yes.'"*

### Comprehension Check (3 min)

1. *"Why does grounding reduce hallucination even though it doesn't retrain the model at all?"* (It changes the model's task from recalling frozen training facts to reading and summarizing text handed to it directly in the prompt — a task LLMs do far more reliably.)
2. *"If RAG is given context that doesn't actually contain the answer, what SHOULD happen, and how do we make that likely?"* (The model should say it doesn't have enough information rather than guess; we make that likely by explicitly instructing it to do so in the prompt template.)

## Q&A & Doubt Solving

**Likely questions and suggested answers:**

**Q: Why use ChromaDB here instead of just looping over all 6 documents and asking the LLM to pick the relevant one itself?**
→ At 6 documents, either approach can work — but RAG's whole value proposition is scaling past what you can stuff into one prompt. A vector store lets you index thousands or millions of documents and retrieve only the handful that are ACTUALLY relevant to a specific query, instead of paying to send (and hoping the model correctly reads) your entire knowledge base on every single question.

**Q: Could we have used FAISS instead of ChromaDB, like Session 9 discussed?**
→ Yes — the RETRIEVAL step is conceptually interchangeable; FAISS is a highly optimized similarity-search library without ChromaDB's built-in document/metadata storage and embedding-function convenience. We used ChromaDB today because its `.add()`/`.query()` API lets us store text and vectors together with less bookkeeping code, which keeps focus on the RAG pattern itself rather than index plumbing.

**Q: Does `temperature=0` completely eliminate any chance of a wrong grounded answer?**
→ No — `temperature=0` makes the model's output more deterministic and less "creative," which helps it stick to the provided context, but it doesn't change WHAT context was retrieved, and it can't force correct reasoning if the context itself is ambiguous or the model misreads it. It meaningfully reduces, but doesn't mathematically guarantee, perfect grounded answers.

**Q: Why join retrieved chunks with blank lines instead of, say, numbering them `[1]`, `[2]`?**
→ Either works, and explicit numbering can genuinely help for a question that needs to compare or cite multiple chunks. We kept it simple today; a common refinement in production RAG systems is prefixing each chunk with its source identifier (e.g., `[Source: doc_id=5]`) so the model's answer can cite exactly which document it used — useful for auditability.

## Common Errors — Quick Reference

| Bug / mistake | Symptom | Fix |
|---|---|---|
| Reusing a collection name/object with already-used IDs | `chromadb` error on `.add()` about duplicate/existing IDs | Create a new, distinctly-named collection, or delete the existing one first with `chroma_client.delete_collection(name=...)` |

| Using a high `temperature` for grounded RAG answers | Answers drift from the provided context more than necessary | Use `temperature=0` (or close to it) for RAG-style factual extraction tasks |

## FAQ — Additional Questions

**Q: Is `n_results` (how many chunks we retrieve) something we should tune, like a hyperparameter?**
→ Yes, very much so. Too few risks missing the one chunk that actually answers the question; too many risks diluting the prompt with irrelevant text and raising token cost. A common starting point is 2-5 chunks, then adjust based on how your specific documents and questions behave.

**Q: Does RAG work for questions that genuinely need information spread across MULTIPLE documents, not just one?**
→ Yes, provided `n_results` is high enough to retrieve all the relevant chunks and the prompt clearly separates them, as our blank-line joining did today. More advanced RAG systems sometimes use multi-step or iterative retrieval for genuinely complex, multi-hop questions, which is beyond today's scope but builds directly on this same foundation.

**Q: If our knowledge base changes (say, CloudNest updates its 2FA policy), do we need to retrain anything?**
→ No — and this is one of RAG's biggest practical advantages over fine-tuning. You simply update `support_docs.csv`, re-run `.add()` (or delete-and-rebuild the collection) with the new text, and the very next query immediately reflects the updated information. No model retraining required at all.
